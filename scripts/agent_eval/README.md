# ②~⑤ 에이전트 평가 (실제 에이전트 코드 + API, 시나리오별 독립 실행)

팀 문서 「② 후보 추천 / ③ 확인 우선순위 / ④ 대응 구매안 / ⑤ 역제안 평가 시나리오」(2026-11-18 개정, 201개)를
**서비스와 같은 코드 경로**로 실행하고 코드로 채점한다.

## 평가 방식

| 항목 | 방식 |
| --- | --- |
| 실행 단위 | **시나리오마다 새 프로세스·새 대화·새 저장소.** 앞 시나리오의 결과가 다음 시나리오에 섞이지 않는다 |
| 실행하는 것 | 서비스의 `AgentRunner` 그대로: 시스템 프롬프트, 도구, 초안 규칙, 최종 검사, LLM 검증자 |
| 숫자 계산 | 서비스 도구(Decimal)가 계산한다 |
| 모델 호출 | OpenAI 호환 API (`EVAL_OPENAI_API_KEY`) |
| 채점 | 최종 응답, 저장된 초안 본문, 도구 호출 기록을 채점 키와 코드로 비교한다 |

DB 대신 메모리 저장소(`store.py`)를 쓴다. 견적 데이터는 손으로 만들지 않고, 메일 원문을 만든 뒤 ①의 저장 함수
(`save_structured_quote`)로 저장해 서비스에서 ①이 저장한 것과 같은 형식이 되게 한다.
웹 검색은 시나리오마다 정해 둔 결과로 바꾼다(실제 검색을 하지 않는다).

## 파일

| 파일 | 내용 |
| --- | --- |
| `scenarios.py` | 시나리오 201개: 세계(업체·품목·견적 메일) + 에이전트 입력 + 채점 키 |
| `world.py` · `store.py` | 시나리오 데이터 빌더, 메모리 저장소 |
| `oracle.py` | **API 없이** 결정적 도구만 불러 시나리오 데이터가 문서 정답과 맞는지 점검 |
| `smoke.py` | **API 없이** 가짜 모델로 실행기 배선 점검 |
| `run.py` | 실행기 (결과: `eval_results/<시각>/runs.jsonl`, `meta.json`) |
| `grade.py` | 채점기 (결과: `summary.md`, `results.csv`). 다시 돌리지 않고 다시 채점할 수 있다 |
| `compare.py` | 두 결과를 시나리오별로 비교 (검증자 켬·끔, 모델, 수정 전·후) |

## 실행 (Windows PowerShell, 저장소 루트)

```powershell
# 0. 처음 한 번: 루트 README대로 .venv를 만들고 requirements 설치

# 1. API 없이 점검 (비용 0)
.\.venv\Scripts\python.exe -m scripts.agent_eval.oracle      # "점검 201개 중 어긋남 0개"가 나와야 한다
.\.venv\Scripts\python.exe -m scripts.agent_eval.smoke

# 2. 평가용 키 넣기 (이 터미널 창에서만 유효. 서버 .env의 LLM_API_KEY는 읽지 않는다)
$env:EVAL_OPENAI_API_KEY = "sk-..."

# 3. 몇 건만 먼저 돌려 비용·시간 확인
.\.venv\Scripts\python.exe -m scripts.agent_eval.run --only C-01 P-01 R-01 O-01

# 4. 전체 (운영 설정 그대로, 시나리오마다 3번)
.\.venv\Scripts\python.exe -m scripts.agent_eval.run --repeat 3 --workers 6 --budget 5

# 5. 채점 (폴더를 주지 않으면 가장 최근 결과를 채점한다)
.\.venv\Scripts\python.exe -m scripts.agent_eval.grade
```

주요 옵션

- `--model`: 역할 ②~⑤의 에이전트 모델을 한꺼번에 바꾼다. 주지 않으면 `app/core/config.py` 설정 그대로다.
- `--verifier-model`: LLM 검증자 모델. 주지 않으면 config 설정 그대로다.
- 추론 수준은 역할별 config 설정을 그대로 쓴다. LLM 검증자도 서비스처럼 붙는다. `--no-verifier`로 끌 수 있다(비교용).
- `--repeat 3`: 시나리오마다 3번 실행한다. `summary.md`에 반복 사이에 결과가 갈린 시나리오가 따로 나온다.
- `--roles C P`: 역할만 고르기. `--only C-01 C-02`: 시나리오만 고르기.
- `--budget 5`: 추정 비용이 5달러에 닿으면 새 시나리오를 시작하지 않고 멈춘다. 처음 4건이 모두 실행 오류여도 멈춘다.
- `--workers`: 동시 실행 수. 속도 제한(429)이 나면 줄인다. API 오류는 `RUN_ERROR`로 분모에서 빠지니 그 시나리오만 다시 돌린다.
- `--langsmith`: LangSmith 기록을 켠다(기본은 끔).

## LLM 검증자의 효과 보기

```powershell
.\.venv\Scripts\python.exe -m scripts.agent_eval.run --no-verifier --repeat 3 --workers 6 --budget 5
.\.venv\Scripts\python.exe -m scripts.agent_eval.compare eval_results\<검증 끔 폴더> eval_results\<검증 켬 폴더>
```

- "B에서 좋아짐" = 검증 덕분에 통과, "B에서 나빠짐" = 검증 때문에 실패.
- `--no-verifier`는 LLM 검증자만 끈다. 코드 규칙(초안 규칙·최종 응답 규칙·최종 검사)은 그대로 돈다.
- 검증자를 켠 실행의 `summary.md`에는 검증자 호출 수, 지적이 있었던 실행 수, 지적 코드가 나온다(`runs.jsonl`의 `verifier`·`draft_gate`).

## 판정

- `PASS`/`FAIL`: 문서의 채점 키와 공통 실패 조건(영문 코드·문장형 사유·"최적"·"추천"·허용 밖 HOLD 등)을 코드로 비교한다.
- `EXCLUDED`: 문서의 채점 제외 행(C-11, C-43, R-48). 실행은 하지만 분모에서 뺀다.
- `SEARCH_MISS`: 검색어로 해당 품목을 찾지 못한 실행(C-05 등). 문서대로 검색 누락으로 따로 센다.
- `RUN_ERROR`: API 키·속도 제한·네트워크 오류. 분모에서 빼고 다시 돌린다.
- 에이전트 쪽 실패(도구 호출 한도 초과, 최종 응답 형식 오류)는 `FAIL`이다.
- 👁 항목은 자동 판정에 넣지 않고 `results.csv`의 "사람 확인" 칸에 적는다.

시나리오 문서와 맞춘 것

- C-25(웹 수집 업체)·C-47(대안 12곳)은 문서에 "데이터 준비 후 실행"이던 것을, 데이터를 만들어 채점에 넣었다.
- P-25·P-26(2026-11-20 팀 판정): 회신 규격 "IQF 다이스 10kg/박스"의 10kg/박스를 박스당 중량의 답으로 인정해,
  업체에 묻는 대신 그 문구를 근거로 다시 추출(RECHECK_SOURCE)하는 것을 정답으로 한다.
- 수치 정답은 `oracle.py`로 201개 모두 실제 도구 계산과 일치함을 확인했다.

## 측정 기록

백엔드 커밋 `38b4ada`(KAN-337 수정 포함). 분모 = 실행 수 − 채점 제외 − 검색 누락. 비용은 `run.py`의 `PRICES` 단가로 낸 추정값이다.

| 날짜 | 모델(②~⑤) | LLM 검증자 | 실행 | 통과 | 역할별 | 추정 비용 |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-11-20 | gpt-6.1-terra | 켬 (gpt-6.1-terra) | 201 × 3 = 603 | **588/591 (99.5%)** | ② 138/141 · ③ 150/150 · ④ 150/150 · ⑤ 150/150 | $3.31 |
| 2026-11-20 | gpt-6.1-terra | 끔 | 201 × 3 = 603 | 전부 통과 (100%) | ②~⑤ 모두 100% | $2.10 |
| 2026-11-20 | gpt-6.1-terra | 켬, 검증자 기록 | 201 × 1 | 196/197 | 검증자 호출 203회, 지적 4건 | — |

- 반복 3회 사이에 결과가 갈린 시나리오는 없었다.
- 검증 켬·끔 비교(`compare.py`): 검증 덕분에 통과한 시나리오 0개, 검증 때문에 실패한 시나리오 1개(C-33).
- **C-33(확인된 문제):** ② 프롬프트는 비고에 배송 제약이 있으면 견적 요청에 `DELIVERY_DAYS`(배송 가능 요일과 지역) 질문을
  넣게 하는데, LLM 검증자는 이 질문을 "이미 답이 있는 질문"(`QUESTION_ALREADY_ANSWERED`)으로 보고 초안을 막는다.
  ②는 그 뒤 견적 요청 전체를 보류(HOLD)해, 검증자를 켠 실행에서 3번 모두 같은 결과가 나왔다.

## 발표에 쓸 때

- 숫자: `summary.md`의 역할별 통과율, 반복 실행 때 결과가 갈린 시나리오 수.
- 함께 적을 조건: 커밋, 모델, 추론 수준, 프롬프트 버전(`meta.json`), 단독 평가(앞 단계 결과는 정답을 넣어 준다).
- 평가 범위: 역할 하나씩의 판단을 본다. 앞 단계 결과가 뒤 단계로 이어지는 흐름은 E2E 테스트가 본다.
