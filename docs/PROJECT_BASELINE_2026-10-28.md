# 견줘 프로젝트 최신 기획 기준 분석

기준: 2026-10-28 10:41 KST 열람 시점. 분석 대상은 메인 Notion **01~07**이다. Notion 리서치 워크플로로 메인 본문·표·Mermaid 텍스트·결과 JSON·인수 조건을 읽고 대조했다. 이는 원문 전체의 파일 내보내기가 아닌 **출처를 연결한 분석·개발 인계 문서**다.

Notion 커넥터는 해당 프로젝트를 찾지 못해, 로그인된 Notion 브라우저의 실제 문서를 읽었다. 열람 중 일부 문서의 공통 안내와 인수 조건이 갱신되어 추가 확인했다. 현재 02의 인수 조건은 AC-01~23이다. 문서에 남은 과거 안내를 최신 요구사항으로 오해하지 않는다.

**이 문서는 새 요구사항의 기준이다. 기존 Python 코드가 이 기준을 구현 완료했다는 뜻이 아니다. 코드·DB 마이그레이션·메일 발송·배포는 이번 작업에서 수행하지 않았다.** 구현 차이는 [별도 분석](IMPLEMENTATION_GAP_2026-10-28.md), 인수 목록은 [검증 기준](ACCEPTANCE_BASELINE_2026-10-28.md)을 따른다.

## 2. 프로젝트 요지와 가치

견줘는 **2차 공급업체의 단가 인상 메일을 받은 1차 벤더 식품업체 구매담당자**가, 이번 조건의 최신 견적을 확보하고 빠진 조건을 확인한 뒤 구매 대응안과 기존 업체 역제안을 판단하도록 지원하는 B2B 서비스다. [01·03]

해결할 문제는 단가 비교만이 아니다. 최신 견적·규격·인증·물량·납기·물류비·거래 근거가 흩어져 다음 행동을 정하기 어려운 문제다. 최종 산출물은 현재 조건의 견적, 근거가 추적되는 검토 카드, 유지/전환/분산 구매안, 기존 업체 역제안, 담당자 판단 기록이다.

에이전트의 가치는 가격 예측이나 임의의 비용 채우기가 아니라 **자료 상태에 따라 조회·질문·안 수정·보류 중 필요한 행동을 고르는 것**이다. 이미 받은 답은 원문에서 찾아 저장하고 재문의하지 않는다. 인간은 최초 실행·조건·발송 정책·예외·최종 판단을 맡는다. [03·07]

과거 거래가격은 인상 타당성·예산·취급 근거로 사용한다. 현재 공급 가능 가격으로 대입하지 않는다. 최신 회신도 적용일·수량·규격·납기·수정 관계를 검증해야 한다. 시장 전체 최저가·공급 품질·시간 절감 효과를 입증한 서비스로 소개하지 않는다.

### Should와 제외

- Should: 허용 공개 출처의 신규 거래처 탐색, 모바일 열람·계정별 기기 캐시. 웹 후보는 별도 잠정 자료이고 회신으로 확인한다.
- 현재 확정된 잔여 Could는 없다. 옛 C 접두어는 과거 ID이며 현재 우선순위를 뜻하지 않는다.
- 제외: 자동 발주·계약·결제, 다회차 자동 가격 협상·독촉, 시장 전체 최저가·품질 보장, 다중 회사 가입/관리, 복잡한 계약·재고 시스템.
- 단일 시연 회사·담당자·Gmail, 한 그룹 한 품목·같은 필수 조건, KRW·근거 있는 단위 환산·동일 세금 기준으로 비교한다.
- 기본 화면은 업무 큐·상세·로그·거래처 기준자료 조회, 원문·초안·진행은 모달이다. 전체 거래처 CRUD와 가격 추이 대시보드는 필수로 확대하지 않는다.

## 4. 업무의 실제 흐름

1. Gmail 푸시 알림을 지속 저장하고 API로 실제 원문·첨부를 확보한다. 경량 LLM 노드는 제한된 입력으로 분류·짧은 사유만 반환한다.
2. 신규 업무만 Work ID와 Waiting을 만든다. 비업무는 큐에 넣지 않는다. 분류/연결이 모호하면 **메일 단위 접수 확인**으로 둔다.
3. 기존 활성 업무의 확실한 회신은 같은 그룹에 연결한다. 수긍·보관 업무의 새 메일은 원문·이력·알림만 남기고 명시 재개를 기다린다.
4. 최초 상세는 원문·첨부 링크만 보여준다. 수긍은 수용·보관 기록이며 분석·후보 조회를 하지 않는다. 다른 대안 찾기가 Running·상세 추출을 시작한다.
5. ① 추출이 원문·첨부를 선택 조회하고 필드·근거·품목 비고를 판단해 검증 저장 도구를 호출한다. 정상값은 수동 재입력·필드별 승인 없이 저장한다.
6. 최초 조건과 정책의 출처를 확인한다. 다음 행동에 꼭 필요한 값이 없으면 NEEDS_INFO다. 분산 허용 미확인은 분산안 제한, 역제안 정책 부재는 역제안 보류로 좁히며 가능한 유지/전환 검토까지 무조건 막지 않는다.
7. ②가 취급 근거·필수 조건으로 후보를 고르고 RFQ 초안을 만든다. 해당 품목 구매 이력이 없다는 이유만으로 취급 근거가 있는 업체를 제외하지 않는다.
8. 서버가 현재 발송 정책·범위·최신 초안·중복을 검사해 승인 ON/OFF에 맞춰 발송한다. 회신 대기에는 LLM 실행을 종료한다.
9. 회신은 자동 수신·그룹 연결·① 추출·새 견적 저장 후 ③으로 재개한다. ③은 원문에 답이 있는지 먼저 보고 필수 누락·역전/분산 영향에 필요한 질문만 묶는다.
10. ④가 KEEP/SWITCH/SPLIT을 구성하고 코드 계산·검증 결과로 수정한다. ⑤가 별도로 유지 목표 가격·조건·역제안을 생성하고 회사 정책 도구로 검증한다.
11. 최신 입력에 맞는 검토 카드를 불변 이력과 함께 저장한 뒤 Complete로 전환한다. 최종 선택·HOLD·확인·보관은 별도 기록이다.
12. 새 근거가 영향을 주면 기존 카드·선택을 남기고 새 revision·검토 라운드를 실행한다. 항상 다섯 역할을 처음부터 반복하지 않는다. [04·07]

## 5. 상태와 행동 계약

| 상황 | 상태·처리 |
|---|---|
| 사용자 실행 전 신규 업무 | `status=Waiting`, `processing_step=PENDING_START` |
| 상세 추출·후보·안 생성 | `Running`, `EXTRACTING`/`SELECTING_CANDIDATES`/`BUILDING_PLANS` 등 |
| 발송 승인 대기 | `Running·AWAITING_APPROVAL`, 실행 종료·이벤트 대기 |
| 회신 미도착 | `Running·WAITING_REPLY`, 자동 독촉·기한 경과 자동 Complete 없음 |
| 카드 전 사용자 HOLD | `Running·ON_HOLD`, 카드 revision=null과 사유 기록 |
| 모델·도구 실패/한도 | `Running·FAILED`, 부분 결과·미해결·실패 보존 |
| 최신 검토 카드 준비 | `Complete·REVIEW_READY`, 최종 구매 선택과 별개 |
| 카드 후 사용자 HOLD | `Complete`, `decision=HOLD` |
| 최초 수긍 | `decision=ACCEPT_INCREASE`, 수용 시각/사용자·보관 기록; 카드 완성과 다름 |
| 카드 확인·보관 | `CONFIRM_REVIEW`는 판단과 보관을 함께 기록; 단순 보관은 판단 변경 없음 |
| 분류 불확실 | 메일 `UNCERTAIN·NEEDS_REVIEW`, work_case_id=null. 업무 Waiting을 만들지 않음 |
| 연결 모호 | 메일 `link_status=AMBIGUOUS`, 임의 병합·발송 금지 |
| 수긍 후 복원 | 복원만으로 분석/발송하지 않음. 명시 `RESUME` 필요 |

메일의 PENDING_START와 업무의 PENDING_START는 각각 ‘상세 추출 전’과 ‘사용자 실행 전’ 의미다. `NEEDS_CLASSIFICATION_REVIEW`를 업무 processing_step으로 저장하지 않는다. 개별 역할 실행의 RUNNING/WAITING_INPUT/COMPLETED/FAILED/STALE도 업무 3상태와 다르다. [06·07, 02 AC-22·23]

실행안이 0개면 사유·미확인·보완/보류를 표시하고 총액·절감액을 추정하지 않는다. 1개면 그 안의 비용만 표시하고 비교 우위를 확정하지 않는다. 2개 이상 유효할 때만 같은 비교 범위의 상대 차액을 표시한다.

문서의 종료 조건은 ‘현재 근거 검토 완료·활성 보완 요청 없음’이다. 실행안 0개의 종료 카드/NEEDS_INFO·ON_HOLD 결과와 Complete·REVIEW_READY 간 정확한 매핑은 후속 08·09 및 팀 결정표로 재확인해야 한다. 미응답·기술 실패를 Complete로 보내는 구현은 허용하지 않는다.

공통 저장은 `save_agent_result`로 최신 입력 버전을 확인한다. 문서 전처리 `preprocess_mail_documents`, 접수 분류 `classify_mail_input`, 실제 발송 `dispatch_mail`, 조정기는 노드다. 노드는 에이전트를 포함할 수 있는 실행 단위이므로 ‘모든 노드가 에이전트’라는 뜻은 아니다. JSON 반환이나 강제로 정해진 도구만 호출한 구현을 다섯 에이전트 완성으로 소개하지 않는다. [07 1·3·4절]

역할별 결과는 `agent_role`, 업무 ID, `input_revision`, `source_quote_ids`, `source_run_ids`, `next_action`, 도구 결과 참조, 미확인·짧은 근거를 갖는다. 구매안 `KEEP/SWITCH/SPLIT`과 역제안 결과는 다른 스키마다. `VALID/CONDITIONAL/INVALID/NEEDS_INFO`를 구분하며 확정 선택은 최신 입력의 VALID 구매안만 허용한다.

같은 모델·SDK·서버를 사용할 수 있다. 별도 조정/검증/계산 LLM을 추가로 요구하지 않는다. 모델·SDK는 여전히 미확정이다.

## 7. 계산·조건 판단 원칙

- 금액·수량·단위·MOQ·포장 배수·단가 구간·배송/기타 비용·세금 기준·공급량·납기·배분·가격 정책은 Python/룰 도구로 계산·검증한다.
- 총액은 배정량에 실제 적용되는 상품금액 + 회사 부담 배송·기타 비용이다. 포함 비용 중복과 계약 잔여 비용 누락을 막는다.
- 배송비 0은 무료 근거가 있을 때만 사용한다. 미확인은 null이며 과거값·임의 범위·확률로 메우지 않는다.
- 최신 견적 선택은 수신 순서/최저가가 아닌 적용일·유효기간·수정 관계·조건으로 판단한다. 최초 인상 메일도 현재 비교 조건에 적용됨이 확인되어야 기존 업체 견적이 된다.
- 필수 인증/규격 불충족을 선호 점수로 상쇄하지 않는다. 품목 비고 자체로 후보 배제·계산·추가 에이전트 실행을 하지 않는다.
- 분산은 최대 2개 업체이고, 배정량마다 공급량·단가 구간·MOQ·포장·납기·운송비가 성립해야 한다. 탐색 범위를 표시하고 전 시장 최적을 보장하지 않는다.
- 역제안의 허용 가격 범위는 회사 정책이다. ‘기존 가격~요청 가격 사이’는 가능한 정책 예시일 뿐 보편 규칙이 아니다.
- LLM 반복 계산·상호 동의는 코드 정답 검증을 대체하지 않는다. 기존 코드의 3회 산식 제안/검증 모델을 새 필수 설계로 유지할 근거는 없다. [02 BR/AIR, 07]

고정 검증 사례는 [인수 목록](ACCEPTANCE_BASELINE_2026-10-28.md)에 기록했다. 0.01원 HALF_UP은 기존 코드 정책이며 새 01~07에서 모든 거래에 적용할 반올림/세금 정책으로 확정됐다고 해석하지 않는다.

## 8. 메일 발송의 계약

- 목적은 `RFQ`, `CLARIFICATION`, `COUNTER_OFFER`; 목적별 대상·승인·스타일·설정 버전을 관리한다.
- 승인 ON은 최종 수신자·제목·본문·초안 ID 스냅샷 승인이다. 수정 시 새 초안·재승인이 필요하다.
- 승인 OFF도 현재 허용 업무·목적·대상·최신 초안·권한·멱등성을 서버가 검증한다. OFF는 제한 없는 Gmail 권한 부여가 아니다.
- 설정 미확정은 `configured=false`로 발송 차단. 업무 목적별 명시 설정 > 메일함 기본값 상속은 제안이며 팀 확정 전 확정 정책으로 구현하지 않는다. null(상속)과 false(명시 OFF)를 구분한다.
- 합성 설정은 목적별 CASE/MAILBOX 원본 ID·버전·합성 settings_version을 보존한다. 단일 FK가 전체 권한 근거를 대신하지 않는다.
- `DRAFT→SENDING→SENT/FAILED/UNKNOWN`. 성공 여부가 불명확하면 UNKNOWN이며 자동 재전송하지 않는다.
- UNKNOWN의 같은 발송 의도(업무·업체·목적·요청 라운드·수정 체인)는 새 초안/키/승인 OFF로도 우회하지 못한다. 대조로 SENT 또는 명확한 미발송/실패를 확정한 뒤만 다음 처리를 허용한다.
- 회신 수신·정규화는 건별 승인이 필요 없다. 자동 발송과 자동 발주·계약 수락·다회차 협상은 다르다. [04·06, 02 AC-15·19·20]

## 9. 아키텍처·저장 모델

Flutter Web(feature-first·Riverpod·GoRouter·Repository·ViewModel) → FastAPI·코드 조정기 → 역할별 LLM/허용 도구 → Supabase Auth/PostgreSQL 및 Gmail 구조다. Gmail은 Cloud Pub/Sub 푸시와 동기화 복구를 사용한다. 수신은 브라우저와 독립적이며 대기 중 LLM 루프를 유지하지 않는다. 별도 업무 브로커·벡터 DB·다중 워커는 필수가 아니다. AWS 서버 1개·Web 정적 호스팅은 배포 예시이며 제품/도메인·계정 배포는 미확정이다. [05]

카드 저장은 최신 입력 검사·review_revision 증가·최신 카드/참조·Complete·REVIEW_CREATED 불변 스냅샷을 원자 처리한다. 과거 지정 revision 조회·stale 표시를 지원해야 한다. 선택은 해당 역할 실행에 속한 최신 VALID plan이어야 한다.

소유자 UUID는 서버 인증에서 정하고 RLS·소유/업무 범위를 검증한다. 업무 ID를 메일 PK로 재사용하지 않는다. Gmail 중복 키는 owner/mailbox/provider_message_id다. 동일 품목명만으로 병합하지 않고 필수 조건·스레드·발송·회사·수량·납기·검토 범위를 확인한다.

파일 본체/Base64·기기 경로·만료 URL을 DB 원본 식별자로 저장하지 않는다. Gmail provider part/attachment ID·메타데이터·원문 위치를 보존한다. 장기 Storage 사본은 보관 정책 확정 후 선택한다. 현재 코드의 필수 EML/첨부 Storage 보존과 별도 전환 결정이 필요하다.

모든 사용자 변경 요청은 발송 키와 별도로 사용자/method/정규화 경로/Idempotency-Key·본문 해시·처리 상태·최초 응답을 지속 저장한다. 동일 요청은 한 번 실행, 같은 키/다른 본문은 `IDEMPOTENCY_KEY_REUSED`, 처리 중은 `REQUEST_IN_PROGRESS`다. 202 최초 접수 응답은 보존하며 진행은 조회한다. 키 보존 기간 확정 전 임의 자동 만료하지 않는다. [06]

## 12. 다음 개발에 사용할 해석

새 프로젝트는 일회성 ‘메일 분석기’보다 **이벤트에 따라 대기·재개하고 최신 거래 근거를 관리하는 구매 검토 워크플로**다. 계산 모듈 일부는 재사용하되 그룹/견적/정책/발송/카드/실행 이력이 먼저 필요하다. 구현은 DB 계약 합의 → 상태/멱등성 → 수신·그룹·원문/실행 → 추출·근거/견적 → 발송/회신 → 우선순위/구매안/역제안 → 카드·선택/로그 → 실계정 인수 순서를 권장한다. 이 순서는 본 분석의 제안이며 팀 일정·완료 약속이 아니다.

태풍 감지·그림자 검토·정기 월별 견적 요청·시간대별 갱신은 이전 대화에서 논의한 아이디어다. 이번에 읽은 01~07의 확정 Must에 자동으로 추가하지 않는다. 외부 가격 수집/웹 탐색과도 구분한다.
