# KAN-74 / KAN-76 implementation and handoff

## Startup contract (KAN-74)

Application creation now fails before serving requests if connection settings are missing or invalid.
Required: SUPABASE_URL, SUPABASE_SECRET_KEY, SUPABASE_PUBLISHABLE_KEY,
GMAIL_CLIENT_ID, GMAIL_CLIENT_SECRET, GOOGLE_TOKEN_ENCRYPTION_KEY.
The Supabase keys must start with sb_secret_ and sb_publishable_ respectively;
legacy JWT service-role/anon keys are intentionally rejected by this ticket's contract.
Encryption key validity is checked locally. Errors print field names only, never values.
Settings parse failures are sanitized too; unidentifiable dotenv errors report ENV_CONFIGURATION.

GOOGLE_MAILBOX_WORKER_ENABLED=true additionally requires LLM_BASE_URL, LLM_API_KEY,
and LLM_CLASSIFICATION_MODEL (or LLM_MODEL). WORKER_ENABLED must remain false.
For polling, leave all four push settings empty. For push, supply all four:
GMAIL_TOPIC, GMAIL_SUBSCRIPTION, PUBSUB_AUDIENCE, PUBSUB_SERVICE_ACCOUNT.
Partially configured push now fails startup instead of silently skipping watch.
This is an intentional behavior change: health/docs-only startup with missing required settings no longer works.

## Receiver (KAN-76)

Existing account-specific refresh-token access, read-scope checks, watch registration/renewal
(within one day of expiration), OIDC verification before enqueue, durable jobs and SQL
deduplication are retained. Push uses the same receiver as polling.
The scheduler checks DB due jobs every five seconds; DB retains its per-mailbox 90-second
due time. This removes an extra process-level 90-second gate that could add another full
poll interval. GOOGLE_MAILBOX_POLL_SECONDS does not override the SQL's due-time policy.
Scheduling interval is not an end-to-end latency guarantee: queue, Gmail and LLM time count too.
